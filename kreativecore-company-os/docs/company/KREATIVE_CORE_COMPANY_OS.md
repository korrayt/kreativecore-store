# Kreative Core Company OS

## Purpose

This document defines how Kreative Core should be understood, organized, developed, tested, marketed, sold, and maintained as a real digital product company.

The repository must be treated as:

- Company digital headquarters
- Product catalog
- Product development surface
- Documentation hub
- Marketing and content platform
- Sales and payment interface
- Release and support surface
- Operational control center

## Core Operating Loop

1. Understand the company and repository.
2. Inventory products and projects.
3. Identify gaps, risks, and opportunities.
4. Define the minimum necessary worker organization.
5. Create focused issues.
6. Assign one accountable owner per issue.
7. Implement in small, reviewable increments.
8. Validate against acceptance criteria.
9. Return failed work for correction.
10. Re-test.
11. Request owner approval for protected decisions.
12. Release.
13. Monitor and maintain.

## Company Analysis Requirements

Before making broad changes, inspect:

- Repository structure
- Branches
- Commits
- Open issues
- Pull requests
- Workflows
- Product pages
- Product code
- Documentation
- Build and release processes
- Payment and delivery paths
- Security and privacy exposure

Report findings under:

1. Current company state
2. Product portfolio
3. Active projects
4. Missing capabilities
5. Technical risks
6. Commercial risks
7. Opportunities
8. Immediate actions
9. Later actions

## Worker Organization

The default organization includes:

- Company Manager
- Product Manager
- CTO
- Frontend Developer
- Product Developer
- Marketing Manager
- Finance & Payment Manager
- QA Engineer
- Security Reviewer

Additional workers may be created only when justified, such as:

- Backend Developer
- DevOps / Release Manager
- UI/UX Designer
- SEO Specialist
- Content & Brand Manager
- Sales & Customer Experience Manager
- Legal & Compliance Reviewer
- AI / ML Engineer
- Product-specific developers

Avoid creating ceremonial roles with no real work.

## Project Classification

Use these statuses:

- idea
- research
- planned
- in-development
- testing
- ready-for-release
- released
- maintenance
- blocked
- deprecated

A product is not “ready” unless code, installation, documentation, testing, distribution, licensing, support, and product-page claims are reasonably aligned.

## Roadmap Stages

### Stage 1 — Stabilization

- Understand the system
- Build the project inventory
- Fix critical defects
- Establish workers and rules
- Validate build and deployment
- Secure secrets and data handling

### Stage 2 — Productization

- Make products installable and supportable
- Complete documentation
- Establish licensing and delivery
- Implement test and release criteria
- Build payment and order flows

### Stage 3 — Growth

- Launch marketing programs
- Improve SEO and content
- Gather customer feedback
- Optimize conversion and support
- Develop new products based on validated demand

## Issue Standard

Every issue should include:

- Goal
- Business reason
- Scope
- Out of scope
- Responsible worker
- Related product
- Files or systems involved
- Dependencies
- Implementation steps
- Acceptance criteria
- Test plan
- Risks
- Owner decisions required

## Error Correction Loop

For every task:

1. Plan.
2. Implement.
3. Test.
4. Compare with acceptance criteria.
5. Diagnose failures.
6. Change the approach when repeated attempts fail.
7. Reassign to the correct specialist when needed.
8. Mark blocked work honestly.
9. Escalate only with a clear technical or business reason.

## Protected Decisions

Owner approval is required for:

- Production payment activation
- Public release
- Pricing changes
- License changes
- Domain or hosting changes
- New paid services
- Large deletions
- Repository deletion
- Material legal or public claims
- Crypto payment activation

## First 30-Day Objective

By the end of the first operating cycle:

- Organization is defined
- Products are inventoried
- Roadmap is active
- Risks are recorded
- Issues have owners
- QA and release gates exist
- Payment architecture is documented
- Product readiness is evidence-based
- Owner decisions are separated from routine execution
